# 体验与使用逻辑审查（2026-10-22）

审查基线：`v1.0.0` / `78aba3d`。下文保留修复前的复现记录与建议，行号对应基线。随后已实现1.0.1补丁，具体实施及证据见 [修复验收](ux-validation-2026-10-22.md)。

## 方法与验证边界

- 使用独立临时目录创建“UX测试-A”“UX测试-B”两组人工构造消息，使用当前源码启动 `127.0.0.1:8099` 控制台。
- 通过浏览器实际点击、切库、保存、切群及刷新验证界面。为复现慢请求，验收服务器对指定读请求/保存请求施加 4 秒延迟；产品请求处理及前端代码保持原样。
- 服务控制、微信探针与邮箱授权使用明确的测试替身；不调用现有 LaunchAgent，不启动真实监控，不读取生产库、不发送真实邮件。共享配置与历史待发任务另用临时文件和假发送器复现。
- 延迟不代表生产环境当前一定有 4 秒延迟；它验证请求乱序时的确定性错误。邮箱假成功验证的是 Windows 未配置时会出现的真实返回结构，浏览器运行在 Mac，本轮未实测 Windows 原生界面。
- 复现脚本及后端结果位于本机 `state/ux-audit/`，不进入发布包。未在本轮重复运行原有全量回归，因为未修改产品实现。

## 已确认的缺陷

P1 表示优先修复的内容/有效配置错误；P2 表示影响信任、输入完整性或流程连续性的问题。

| 编号 | 优先级 | 问题 | 证据 |
| --- | --- | --- | --- |
| UX-01 | P1 | 切库后旧请求覆盖新列表，来源与选择器不一致 | 浏览器受控乱序复现 |
| UX-02 | P1 | 跟随共享配置时，保存或切换处理方式不作用于实际配置源 | 两个方向的临时配置复现 |
| UX-03 | P2 | 切监控群后刷新，会再次选中旧群历史库 | 浏览器实际切群、刷新复现；服务操作为测试替身 |
| UX-04 | P2 | 邮箱未配置仍显示“授权完成”，且 Windows 路径显示 Keychain 提示 | 实际平台分支返回值 + 浏览器响应替身复现 |
| UX-05 | P2 | 保存过程中输入的新草稿被响应覆盖 | 浏览器延迟保存复现 |

### UX-01：慢请求导致跨群内容错配

位置：`wechat_tracker/resources/web/app.js:362`（`loadEvents`）、`:616`（`loadOutbox`）、`:894`（`openEmailPreview`）。

复现：先显示 B 库 → 选择 A 库，A 查询延迟 4 秒 → 立即再选 B 库。B 查询先完成，随后 A 的旧响应返回。

实际观察：选择器保持“历史只读库 - UX测试-B”，列表标题却变成“A组唯一讲座”，原文来源和报名链接均为 A 群；投递横幅也变回 A 群。点击该卡片的邮件预览，显示 `Event or Job not found`。邮件队列的本地 job ID 还可能在不同库相同，进一步造成所见记录与预览内容不一致。

原因：请求返回时仅检查控制台是否关闭，没有保存并核对请求的数据库身份/请求序号；还会将旧响应的数量写到当前选择器选项。`loadMessages` 已有请求序号与数据库核对，可以统一采用相同原则。

修复建议：为事件、队列、预览统一绑定“数据源 + 请求代次”；切库时立即清理旧列表，展示加载状态，取消旧请求并忽略所有迟到响应。加载失败时明确保留的是哪个库的旧数据，不能只弹短暂错误提示后继续显示可操作旧卡片。

验收：A 慢/B 快和 A 快/B 慢均不出现错配；切库失败时旧内容不被当作新库结果；卡片预览与卡片创建时的数据库身份一致。

### UX-02：共享设置保存成功但不生效

位置：`wechat_tracker/extraction/settings.py:66`（有效配置解析）、`:126`（保存）；`wechat_tracker/console/handler.py:371`（处理设置接口，具体以函数名定位）。

复现：跟随配置含 `processing_config_path = "shared.toml"`。共享源为 rules，在跟随配置保存 llm；反向再测试共享源为 llm、跟随配置保存 rules。

实际结果：

```json
[
  {"shared_mode":"rules","requested_mode":"llm","effective_mode_after_save":"rules"},
  {"shared_mode":"llm","requested_mode":"rules","effective_mode_after_save":"llm"}
]
```

原因：读取会转到共享源，保存却总写当前跟随配置及其密钥文件。接口返回成功，前端也提示已保存，但下一条消息仍采用共享源。尤其点击“本地规则”后有效模式仍为 llm，会使用户误判后续消息的处理方式。本轮未向任何外部模型发送消息。

修复建议：读、保存、测试、清除密钥共用一个明确的配置来源解析器。跟随配置页面默认显示“由共享源管理”，并提供跳转到来源设置的入口；若允许修改共享源，必须明确受影响的群和服务。不要静默修改全局来源，也不要静默写入无效的局部覆盖。

验收：成功提示对应的有效设置必须与下一条消息实际使用的一致；无法在此页面修改时明确拒绝。规则/LLM 两个方向和密钥更新/清除都覆盖，共享影响范围可见。

### UX-03：群切换没有同步持久化的数据源选择

位置：`app.js:12`、`:342`、`:1444`。

复现：明确选择 A 活动库，使选择写入浏览器存储 → 将监控群切换为 B → 页面当时正确显示 B 活动库 → 刷新页面。

实际观察：顶部“当前监控的目标微信群”是 UX测试-B，数据源却恢复为 UX测试-A 历史库，内容也显示 A 的通知。切群本身成功，错误在刷新后的视图恢复。

原因：下拉选择会写 `localStorage.selectedDatabase`，切群成功只清空内存状态，不更新/清除持久值。旧群历史仍在列表内，刷新时被当作有效的记忆选择。

修复建议：统一一个数据源选择函数处理状态、持久化、列表清理和重新加载；成功切监控群时原子地选择并记住新活动库。浏览器记忆按当前配置/监控实例区分，避免同端口更换配置后沿用另一份配置的视图。

验收：切群成功后立即刷新或关闭重开，均默认显示新群活动库；明确选择历史视图的行为另行保留，不能与切监控群混为同一个操作。

### UX-04：邮箱授权假成功与首次配置入口缺失

位置：`app.js:1484`；`wechat_tracker/credentials.py:120`；`resources/web/index.html:512`。

后端实际分支：非 macOS 时 `authorize_credentials` 返回 `configured = apply_credentials(config)`；未保存凭据、环境变量也未设置时返回 `false`，并不抛错。

浏览器复现：模拟该合法响应 `{ok:true, configured:false, smtp_sent:false}`，点击“授权邮箱”。页面仍显示“邮箱授权完成，后台会自动重新加载”，同时配置区继续显示“尚未配置邮箱”，且提示去系统钥匙串操作。代码未读取 `configured`。

此外，首次没有配置邮箱时，页面只有“授权邮箱”而没有设置地址/授权码或指向初始化命令的明确入口；macOS 实际会报“请先配置邮箱”，用户只能自行查文档找到 CLI。

修复建议：区分“未配置”“已保存但未授权”“可用”状态。首次使用展示本机配置入口或可复制的正确命令；Windows 用 DPAPI/环境变量措辞，Mac 才显示 Keychain 授权。根据返回状态确认结果，授权成功与真实邮件送达分别展示。

验收：`configured=false` 不出现成功提示；两平台文案正确；用户能从未配置状态走到可用状态，无需猜测先后步骤。

### UX-05：保存响应覆盖正在编辑的新草稿

位置：`app.js:1227`、`:1233`、`:1190`。

复现：模型名称改为 `draft-before-save` → 点保存（请求延迟 4 秒）→ 保存期间输入框仍可编辑，改成 `draft-typed-during-save` → 等待成功响应。

实际观察：响应前输入框显示新文本；响应后恢复为 `draft-before-save`，同时显示“已持久保存”，后续草稿不再保留为未保存。保存成功分支还会清空密钥输入框，采用同样的草稿处理逻辑。

原因：只禁用按钮，没有冻结字段；响应回来后无条件清除 dirty 标记并强制回填保存前的快照。

修复建议：保存时冻结相应表单，或记录草稿版本；仅当草稿未发生后续变化才清理 dirty/回填。允许继续编辑时，应显示“上一版已保存，当前仍有未保存修改”。

验收：慢保存期间继续编辑不会丢字；失败保留草稿；新输入的密钥不被旧响应清空；重复保存结果顺序可预测。

### UX-06：Demo 邮件显示成需要启动服务解决的故障

位置：`wechat_tracker/console/handler.py:147`；`console/presentation.py:4`；`app.js:628`、`:1572`。

复现：在配置页运行 Demo，再查看讲座消息。页面标注“Demo 演示库（只读）”，但横幅显示“UX测试-B：等待服务启动”，卡片解释为“通知已入队，所属群的监控服务未运行”。Demo 的来源群与本次管理群还并不相同。

原因：投递服务仅按数据库父目录匹配，`demo.sqlite3` 与真正的 `tracker.sqlite3` 位于同一目录时被视为同一个服务库。投递状态函数也不知道这是演示任务。模拟运行“发信就绪”的服务时，同样的演示任务被标为“排队时间较长”。

影响：用户可能为解决演示“故障”而启动真实监控或切到发信模式，但真实服务只调度自己的 tracker 库，无法解决演示任务状态。

修复建议：投递归属按完整数据库身份匹配；Demo 返回显式 `simulation` 状态，统一解释“仅验证预览，永不投递”。演示结果不要显示真实服务的故障修复指引。

验收：真实服务停止、预览、发信三种状态下，Demo 均清晰标注演示，不显示待启动、待凭据、排队超时，不计入真实待发提醒。

## 可以优化的使用逻辑

### 1. 开启发信前，先说明旧的待发任务如何处理

位置：`app.js:1500` 与 `application/delivery.py:16`。

这项是行为预期与确认信息的缺口，不能简单判定为调度算法错误。当前确认框只说“捕获到讲座时将发送”，但调度器会处理所有已到期、策略有效的 pending 通知。

已用两周前的人工构造通知与假发送器验证：切到 `send=True` 后，该旧通知进入假发送器一次，任务记为 sent；真实 SMTP 连接数为 0。旧记录并不一定只作为历史保留。

建议确认页显示：当前作用群、即将处理的待发数量、最早时间、是否有重试/积压。可选择发送已有待发，或明确把既有待发标记为用户跳过后只处理后续消息。跳过应留审计记录，不直接删除原始消息或队列。

### 2. 把“管理哪个群”和“正在查看谁的记录”分开

现在顶部服务控制始终作用于当前配置；数据源可指向另一个群或 Demo。建议使用两个清晰区域：

- 管理区：当前监控群、窗口可读性、最近成功采样、邮件模式；所有启动/停止按钮带作用群名。
- 浏览区：当前/历史/演示记录。历史模式持续显示“正在查看 A 历史；监控操作仍作用于 B”，提供“返回当前群”按钮。

查看历史记录时，不让“立即调度”等看似作用于所选记录的全局操作混在列表工具栏里。

### 3. 首次使用变成逐步完成的流程

建议顺序：选择精确群名 → 探测窗口 → 启动预览 → 在采集消息里确认原文 → 查看通知预览 → 可选配置邮箱 → 确认待发范围后开启真实发信。

首页突出“服务在运行”“窗口可读”“最近采集成功”“邮箱可投递”四个不同事实。模型超时、密钥环境变量、SQLite 日志模式等放入高级设置。不要让用户把进程在线误认为消息采集正常。

### 4. 让失败任务有明确的恢复路径

目前页面可看错误和重试时间，但 dead 任务没有直接恢复入口；顶部“触发即时调度”实际调用的是 `dispatch(send=False)`，只计算预览，成功提示中的“处理任务数”容易让人误以为已经投递。

建议将该按钮明确命名为“预览到期任务”；若需要真实重试，独立提供带群名/数量的显式操作，保持任务领取与重复发送边界。区分“自动重试中”“已停止重试”“被用户跳过”，分别给出修复设置、重试、忽略的下一步。

## 修复顺序与回归范围

1. 第一批：UX-01 请求归属与加载状态；UX-02 有效配置来源；真实发信前的积压说明。
2. 第二批：UX-03 切群持久化；UX-04 邮箱配置/授权状态；UX-05 草稿保存。
3. 第三批：UX-06 演示语义；管理区/浏览区分离；首次引导与失败恢复入口。

新增验收应包含浏览器异步场景：请求乱序、保存时继续输入、切群后刷新、错误响应保留旧内容、配置共享及不同平台授权返回。原有后端回归通过不能替代这些流程测试。
