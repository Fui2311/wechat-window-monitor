# 数据库可靠性调查与恢复

2026-10-15，服务崩溃恢复测试后追加 SQLite 完整性检查，发现原 WAL 数据库 `database disk image is malformed`。此前单纯检查活动/队列数量不能证明数据库完整，相关初步恢复结果不再单独作为可靠性验收依据。

已核实命令行和计划任务都使用 Anaconda Python 3.11.7、SQLite 3.41.2、相同 SQLite DLL。库出现了旧页面状态与队列表损坏；部分消息、活动、采集缓存和缺口表仍可读。故障根因尚未复现到 SQLite 内部级别，不能断言一定来自某一已知缺陷。

SQLite 官方记录了 [WAL-reset 并发损坏问题](https://www.sqlite.org/wal.html#walreset)：旧版本在多连接并发写入或 checkpoint 的特定竞争条件下有风险，3.51.3 及后续版本修复。本机运行库和访问方式落在风险范围内，因此本项目选择不依赖 WAL：单写者、低频消息适合 DELETE 回滚日志与 FULL 同步。

恢复步骤已实际执行：

1. 暂停计划任务，保存原数据库、WAL/SHM、健康文件与日志副本；不覆盖或删除故障证据。
2. 导出可读消息、缓存与缺口记录，重新导入此前核对过的原始转发 JSONL。
3. 由于 QQ 凭据尚未配置、实际发送数始终为0，本次可以按源消息重建待发队列；已发送邮件的数据库不能照此盲目重放。
4. 新库 integrity_check 为 ok，创建并检查 last-good 备份后恢复服务。
5. 再次实际终止生产服务，19.11 秒后新实例自动恢复；持续检查新库完整性为 ok，前后消息7、活动4、队列8均不变，旧采集进程未残留。缺口增加1条，符合预期。

本机证据在 Git 忽略目录 `state/db-investigation-20261015-151820/` 与 `state/service-crash-recovery-after-db-repair.json`；原故障数据库另保留在生产数据目录，文件名含 `corrupt-20261015-1524`。部分缺口历史只能由外部日志/验证摘要追溯，本次不声称完整恢复了所有损坏页。

长期行为新增：启动完整性检查，失败时状态为 database_error 并停止；每小时通过 SQLite backup API 保存校验过的快照，同时保留前一份。自动启动不会静默清除故障数据库。

新增回归测试实际创建未提交事务、强制终止子进程，再次打开验证已提交状态保留、未提交状态回滚、完整性和备份可读；损坏文件保持原样并拒绝启动。通过测试及一次生产重测仍不能代替24小时、真实消息高峰和硬件断电验收。
